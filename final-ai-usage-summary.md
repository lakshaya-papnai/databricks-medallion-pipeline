## 3 Most Impactful AI Contributions

**1. `concat_ws()` multi-failure pattern in Silver**
The approach of building a composite `quality_check_result` string using `concat_ws(", ", when(cond1, lit("reason1")).otherwise(None), ...)` allowed a single row to carry multiple failure reasons without duplicating it. This was the correct PySpark idiom and is reusable across any quality-checking pipeline.

**2. `PERCENT_RANK()` for High-Value customer segmentation**
Rather than an arbitrary percentile cut using `NTILE()`, AI suggested `PERCENT_RANK() OVER (ORDER BY total_revenue DESC)`, which produces a continuous rank value. This is semantically correct — it ranks customers relative to the full population and cleanly identifies the top 20% regardless of revenue distribution shape.

**3. `importlib` for number-prefixed module orchestration**
Python cannot import modules whose names begin with digits using standard `import` syntax. AI immediately identified `importlib.import_module("01_ingest_customers")` combined with `sys.path.append(os.path.dirname(__file__))` as the correct solution. This pattern was reused identically in three orchestrator scripts.

## 2 Cases Where AI Output Needed Correction

**1. Silver orchestrator join on single key (corrected to compound key)**
`create_silver_tables.py` initially joined quality-check tables on `customer_id` alone. Because Bronze tables preserve duplicate `customer_ids` (10 planted), joining on a non-unique key causes row fan-out — one row matching multiple rows in the next table, inflating row counts. The fix was to join on `customer_id + ingestion_timestamp`, which together uniquely identify a row. This was caught during design review of the join logic.

**2. Products validation too thin (profiling section added)**
`03_ingest_products.py` initially replicated the same NULL count and duplicate count validation from the customers and orders scripts. Since products has zero intentional issues, both counts would always be zero — meaningful for confirming correctness but not useful as a sanity check on the data content. A numeric range profiling section (min/max for price, cost, stock_quantity) was added to provide genuinely informative validation output.

## Responsible AI Use

No real customer data, production database credentials, or personally identifiable information was shared with the AI tool at any point. All data used in development is fully synthetic, generated by `generate_sample_data.py` using the `Faker` library with a fixed seed (`42`) for reproducibility. Synthetic data was chosen specifically because it allowed realistic data quality issues to be planted by design rather than discovered by accident, and because it eliminates any risk of data leakage through AI tooling. The AI tool was used only with project structure, schema definitions, and code logic- none of which represents sensitive business information.
