# Reflection — AI-Assisted Medallion Architecture Pipeline

**Project:** E-Commerce Data Pipeline (Bronze → Silver → Gold → Dashboard)
**Tools used:** Cursor (Claude Sonnet 4.6)
**Assessment Part:** C — Submission and Reflection

---

## 1. What I Built

I built a complete Databricks medallion architecture data pipeline for an e-commerce company. It processes daily sales data from three CSV sources across four layers.

**By the numbers:**
- 3 source tables — customers (10,010 rows), orders (100,020 rows), products (500 rows)
- 3 Bronze Delta tables for raw ingestion (added metadata columns, no transformations)
- 8 intermediate Silver quality-check tables that feed into 3 final Silver tables. These are all quality-flagged with a `quality_check_result` column.
- 5 Silver quality checks — completeness, uniqueness, referential integrity, type validation, business logic
- 6 Gold Delta tables generated by 4 aggregation scripts for business analytics
- 5 dashboard SQL queries powering various charts (bar, histogram, pie, line, stacked bar)
- Caught all 460 intentionally planted rows across 7 issue types exactly.
- Wrote 21 source files in `src/`, fully commented.

And honestly, beyond the minimum requirements, I decided to add a fifth Silver check (business logic validation for amounts and dates) and a fourth Gold table pair for daily and weekly revenue trends. Neither was strictly required, but it felt incomplete without them.

---

## 2. How I Used AI Across the Lifecycle

AI wasn't just a generic code generator here. Its role shifted as the project moved forward.

**Planning and design:**
I used AI mostly for structuring early on. I gave it the business problem and schemas and had it draft `requirements-analysis.md`, `data-quality-strategy.md`, and `data-model.md` before I wrote any code. Front-loading the design was intentional — having those docs meant I could just point the AI to them later instead of constantly re-explaining the context. Setting up a `.cursorrules` file early on and keeping it active was easily the main thing I kept coming back to.

**Data generation:**
I had AI write the `generate_sample_data.py` script based on a pretty detailed spec. The logic to make sure the planted issues didn't overlap by partitioning a sample of 400 indices from the 100,000 rows was something it handled perfectly without me needing to design it out step by step. But I still ran manual Python checks against the generated CSVs before trusting the data for the pipeline.

**Bronze layer:**
I asked AI to write `01_ingest_customers.py` completely, setting up a 7-section structure with comments. For the next two Bronze scripts, I just told it to "follow the exact same structure." Reusing it by reference saved a ton of time and kept things consistent.

**Silver layer:**
This is where AI actually saved me from a lot of headache. Dealing with window functions like `ROW_NUMBER()`, LEFT JOINs for referential integrity, and using `concat_ws()` to build composite failure strings would have taken me way longer to get right from scratch. I gave it the fields, the thresholds, and the output format, and it usually nailed the PySpark idioms on the first try.

**Gold layer:**
AI wrote the aggregation SQL using `spark.sql()` with temp views. I personally find that way cleaner than chaining a bunch of PySpark API calls for reporting logic. The `PERCENT_RANK()` approach for High-Value segmentation was actually the AI's idea based on my spec — I just described what I wanted, not how to do it.

**Dashboard:**
I gave it the five query specs and it generated clean SQL. I didn't change the core logic much, but I did have to review each query against `schema.sql` to make sure the column names actually matched.

**Documentation:**
AI drafted most of the documents. Cursor kept writing everything in this weirdly formal tone, so it took me a while to just rewrite sections to sound like something I'd actually say, especially in the lessons learned stuff.

## 3. What AI Helped With Most

**1. The referential integrity LEFT JOIN logic**
The tricky part wasn't the join, it was the condition. Rows where `customer_id` is already NULL shouldn't be flagged as orphans; the completeness check catches those. AI got this right away: check `customer_id IS NOT NULL` before seeing if the join produced a match. I probably would have missed that edge case on my first pass.

**2. The `concat_ws()` pattern for multi-failure rows**
If an order row has both a NULL `customer_id` and a NULL `product_id`, the flag needed to say `'FAIL - NULL customer_id, NULL product_id'`. AI suggested using `concat_ws(", ", when(...), when(...))`. This pattern silently drops NULL values and was way cleaner than whatever nested IF statements I was going to try.

**3. The `importlib` pattern for number-prefixed module names**
My scripts are named stuff like `01_ingest_customers.py`, which are invalid Python identifiers. You can't just `import` them normally. AI immediately suggested using `importlib.import_module()` and appending to `sys.path`. I used this exact pattern for the Silver and Gold orchestrators too.

**4. `PERCENT_RANK()` for High-Value segmentation**
I said "top 20% of customers by revenue should be High-Value." It gave me `PERCENT_RANK() OVER (ORDER BY total_revenue DESC)` and explained that rank 0.0 is the top earner, so `<= 0.20` gets the top 20%. I was originally thinking about using `NTILE(5)`, but `PERCENT_RANK` makes more sense here since it's a continuous value instead of discrete buckets.

## 4. What AI Got Wrong or Needed Correction

I want to be honest here because this is where I actually learned the most.

**1. Silver orchestrator join fan-out risk**
In `create_silver_tables.py`, the `combine_quality_flags()` function joins multiple per-check tables on the primary key (like `customer_id`). The issue is that the Bronze tables contain duplicate IDs (the 10 I planted). Joining just on `customer_id` would fan out and multiply the row count. The fix was joining on both `customer_id` AND `ingestion_timestamp`. AI didn't suggest this — I spotted the risk and had to tell it to use the compound key.

**2. Products validation was too thin initially**
The first pass at `03_ingest_products.py` just printed NULL and duplicate counts, copying the pattern from the other scripts. But products has zero intentional issues, so it wasn't very useful. I had to manually add a data profiling section (min/max for price, cost, etc.) to make it actually meaningful.

**3. Uniqueness threshold phrasing**
In the data quality strategy doc, AI wrote "Threshold: 100% unique". But when you run it against orders with 20 duplicates in 100k rows, the pass percentage is 99.98%. The phrasing needed to mean "any duplicate is a failure," not that we expect the final pass rate to be 100%. I updated the doc to say "threshold for acceptable data = 100% unique; pass rate will reflect actual duplicate count" so it wouldn't confuse anyone reading the final report.

## 5. How I Validated AI Output

I made sure validation was a core step at every stage, not just an afterthought.

**Data generation:** Before running the pipeline, I wrote some quick Python validation commands to check every planted issue against its exact expected count. All 460 issues matched perfectly.

**Bronze layer:** The end of each Bronze script reads back from Delta and prints the counts. The important part was checking that these matched the raw input, proving no accidental cleaning happened during the load.

**Silver layer:** I printed actual vs expected counts at the end of every Silver check. Formatting it as `(expected: 50)` right next to the actual count made it super obvious if something broke in Databricks.

**Code review against .cursorrules:** I was strict about checking any generated script against the rules in `.cursorrules`. Especially making sure Silver scripts only read from Bronze Delta (not CSVs), no rows were deleted, and paths used `/FileStore/`.

**Schema cross-check:** I went through `schema.sql` and manually compared every column name and type against the PySpark code to make sure they lined up. Caught a couple minor mismatches that way.

## 6. What I Would Improve Next Time

**1. Run the pipeline in Databricks earlier — much earlier**
I basically wrote all the code before running any of it in Databricks. Path issues, table registrations for the dashboard, and cluster stuff only popped up at the very end. Next time I'd run a skeleton version of each layer as soon as possible.

**2. Write validation assertions before code (test-first)**
If I had written `assert null_email_count == 50` in a test file before writing the Silver completeness check, that join fan-out bug would have been caught immediately. Writing validations after the code is just the wrong order.

**3. Split `create_silver_tables.py` into smaller pieces**
The `combine_quality_flags()` function in the Silver orchestrator is doing way too much: iterative joins, renaming columns, building failure strings, writing results. It's annoying to read and debug. Splitting it into smaller helpers like `combine_customer_flags()` would be much cleaner.

**4. Use MERGE instead of overwrite for incremental loads**
Everything uses `mode("overwrite")`, which replaces the whole table. For a daily batch pipeline this works, but in real life you'd use Delta's `MERGE INTO` to insert/update rows without reprocessing everything. It was out of scope for this assessment, but it's the first thing I'd change for production.

## 7. Reusable Workflow Patterns I Developed

These are a few patterns I'm definitely keeping for future AI projects.

**`.cursorrules` as persistent context file**
Putting schemas, hard rules, and a progress tracker in `.cursorrules` meant I never had to repeat myself across sessions. The context was just always there. 

**One file at a time prompt pattern**
Telling the AI to only generate one file per response stops it from dumping a huge mess of code all at once. Smaller chunks mean you actually review it properly.

**Expected vs actual counts in every validation output**
Printing `(expected: 50)` next to the actual count is a lifesaver. It turns the output from "data you have to analyze" into "data that self-diagnoses."

**Orchestrator pattern with fail-and-continue**
Separating the logic scripts from the execution scripts (`ingest_all.py`) makes it clear what's happening. The try/except blocks in the orchestrators mean one broken script doesn't silently block the rest, but it still triggers a `sys.exit(1)` for job alerts.

**Prompt log template**
Using a format like PROMPT SENT → AI RESPONSE → WHAT I ACCEPTED → FINAL DECISION forced me to think about what I was actually accepting instead of just blindly copying code. It really helps you stay in control.
